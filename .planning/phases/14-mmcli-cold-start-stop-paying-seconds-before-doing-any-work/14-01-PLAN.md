<objective>
Stop `mmcli` spending 2.6 seconds detecting a training device it usually does not need.

**Fully measured — REQ-COLD-02 is already answered, do not re-derive it:**

```
_detect_training_device() called 3x, total 2.60s for `mmcli --version`
```

`0.02s` imports + `2.60s` detection = the 2.75s source-run figure. Nothing is unattributed.

Three call sites, all reached before any command runs:
- `cli.py:411` inside `_add_training_args()`, invoked at **`:743` and `:819`** — once per subparser.
  argparse builds every subparser eagerly, so **every** invocation pays for all of them.
- `cli.py:2150` inside `main()`, before argparse is constructed.
- (`cli.py:1910` is in `_print_full_help`, only on the full-help path.)

Each call runs `system_profiler SPDisplaysDataType` — 0.90s standalone, uncached between calls.
Its own macOS fallback is *"any macOS likely has Metal" → `mps`*, which is what the probe returns
in practice anyway.
</objective>

<task type="auto">
  <name>Task 1: detect at most once, and only when the answer is needed</name>
  <files>mmcli/cli.py</files>
  <action>
Two independent problems; fix both, and keep them distinguishable in the diff.

**(a) It runs more than once.** The result is a constant for a machine within a process. Memoise it
so repeated calls cost nothing. This alone takes 2.60s → ~0.87s.

**(b) It runs when nobody needs the answer.** `--version` and `--help` do not need a training
device. The value is used to shape argparse *defaults*, which is why it happens eagerly. Make the
default lazy so the probe runs only when a command actually consumes it.

Prefer whichever of (b)'s approaches keeps `--help` output honest: if the help text currently shows
the detected device, decide deliberately whether it still should. Showing a stale or absent value in
help would be worse than a slightly slower `--help` — say what you chose and why.

**Do not change what is detected.** The device selected for a real training run must be identical
before and after; this is a *when* and *how often* change, not a *what* change. Any behavioural
difference is a finding to report, not a fix to make.

Keep `system_profiler`'s existing 3s timeout and the fallback chain intact.
  </action>

Add a test that fails if the eager, repeated behaviour comes back.

**Count calls, do not measure wall time.** A timing assertion is flaky on a loaded machine and would
be exactly the kind of test people learn to ignore. Patch or instrument
`_detect_training_device` and assert it is called **at most once** for `mmcli --version`, and **zero
times** if you made it fully lazy for that path.

The instrumentation pattern that produced the measurement above works — a counting wrapper around
the function, then invoking `main()` with `sys.argv` set and catching `SystemExit`.

Prove the test is not vacuous: confirm it fails against the current eager implementation (e.g. by
temporarily reverting Task 1, or by asserting the count is what you actually observe). Say in the
SUMMARY how you established that. An assertion that passes whether or not the fix is present is
worth nothing, and this repo has been bitten by that twice this week.

Docstring must explain *why* — that this probe shells out to `system_profiler` at ~0.87s a call and
was running 3× per invocation, so a future refactor that reintroduces eager detection is caught
here rather than by a user noticing mmcli feels slow.
