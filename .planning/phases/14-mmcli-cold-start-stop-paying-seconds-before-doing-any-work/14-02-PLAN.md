  <files>.planning/phases/14-mmcli-cold-start-stop-paying-seconds-before-doing-any-work/14-02-SPIKE.md</files>
  <action>
List every place that assumes mmcli is one file. Start from the three known sites above and
**search for more** — release workflow, docs (`docs/RELEASING.md`), the Phase 10 size gate and its
tests, `PlatypusStudio`'s resolution and copy path, and anything in `tests/` that shells out to
`dist/mmcli`. For each: what changes, and how much work.

Note the asymmetry explicitly, because it drives the recommendation: **the app copies the binary
into Application Support once and would copy a directory just as easily** (`copyItem` handles
directories), whereas a CLI user downloading a release asset currently gets one file they can drop
anywhere. Those two consumers do not want the same thing.

So evaluate at least three options, not two:
1. Stay onefile — accept ~3.86s.
2. Move everything to onedir — fastest, but changes what users download.
3. **Hybrid** — onedir for the app's managed copy, onefile for release downloads. Two artifacts
   from one build. Assess whether the build and release complexity is worth it.

End with a **recommendation and the reasoning**, plus what you would need to know to be more
confident. Do not present it as a decision already taken — Martin decides, and REQ-COLD-03 exists
precisely because "faster" is not automatically "better" here.

Quantify against the existing budget: REQ-SIZE-01 requires start < 8 s and we are at 3.93s. If the
current state already satisfies every stated requirement, say so plainly — that materially weakens
the case for any change and is the kind of thing easy to lose sight of mid-optimisation.
