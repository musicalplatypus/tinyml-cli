  <files>mmcli/cli.py, mmcli/builder.py, tests/test_advanced_training_knobs.py</files>
  <action>
`training.run_quant_train_only` exists in all four modelmaker modules and is not reachable from
mmcli. Semantics, read from source rather than assumed
(`ai_modules/timeseries/training/tinyml_tinyverse/timeseries_base.py:896-912`, and the parallel
sites in vision/audio/radar):

- When true, the **float training pass is skipped** and only the quantisation training pass runs.
- It **raises `ValueError` when `quantization == NO_QUANTIZATION`**. That is a hard precondition,
  and today it would surface as a Python traceback from deep inside modelmaker.

Add a `train` flag for it. It is a training knob, not a subcommand — it modifies how `train`
behaves rather than being a separate pipeline.

**Enforce the precondition in mmcli, with a clear message.** PROJECT-level: users should not need
to know modelmaker's internals. A flag combination that provably cannot work should be rejected at
argument-parsing time naming both flags, not after the subprocess starts. Follow whatever
convention `cli.py` already uses for mutually-incompatible flags — survey it first rather than
inventing one.

Follow the established emission pattern: `_set()` skips `None`, so the key must be **absent** when
the flag is not passed. That is not incidental here — plan 13-01 pins exactly this rule for the
adjacent keys, and this new knob must not become the exception.

Tests: the flag emits the key when passed and omits it when not; the incompatible combination is
rejected with a message naming both flags.
  </action>
