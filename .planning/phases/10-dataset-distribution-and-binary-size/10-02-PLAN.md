<objective>
Let datasets be fetched from TI's download server on demand, pinned to a TI engine version,
verified by digest, and cached — so the binary no longer has to carry them and a dataset can
be release-specific.

Purpose: this is the mechanism 10-03's unbundling depends on. It also introduces the only
remote-fetch surface in a tool that then runs training jobs, so integrity is a requirement of
the mechanism, not a follow-up.
Output: registry fields, a version-scoped cache, and `fetch_dataset()` with mandatory
verification. The `datasets` CLI subcommand that exposes all of this is plan 10-06.
</objective>

## Background

Decisions D-1 through D-4 are settled in `10-RESEARCH.md`, so this plan is unblocked.

`mmcli/datasets.py` already has the seam: `_datasets_dir()` (line 18) resolves
`MMCLI_DATASETS` first and falls back to the bundled directory, `DATASET_REGISTRY` (line 35)
holds one record per dataset with keys `filename`, `task_types`, `module`, `description`, and
`extract_dataset()` (line 166) is the only place a zip is opened. There is no download path
today and no `url` or `sha256` key on any entry.

The change is additive — `MMCLI_DATASETS` and the bundled directory keep their existing
precedence, so nothing regresses for managed environments.

**Versioning (D-1/D-3/D-4).** TI version-paths its datasets, so the URL shape is
`https://software-dl.ti.com/C2000/esd/mcu_ai/<VER>/datasets/<ti_name>`. Five local names
differ from TI's, so each entry carries both `filename` (local/cache name) and `ti_name`. A
module-level `DATASETS_DEFAULT_VERSION` supplies the version; an entry may override with
`ti_version`. `generic_audio_classification` is locally authored, has no `ti_name`, and stays
bundled.

Add `_cache_dir(version)` returning `<XDG_CACHE_HOME or ~/.cache>/mmcli/datasets/<version>`,
created lazily with mode 0700.

**The version must be part of the path.** A flat cache would let a version bump silently
reuse a dataset from an older TI release — the exact failure D-3 exists to prevent.

Add a single resolution function that `extract_dataset()` and the CLI both call, ordering:
`MMCLI_DATASETS` → bundled `example_datasets/` → `_cache_dir(version)` → not present
(caller decides whether to fetch). Keep `_datasets_dir()`'s existing behaviour intact so
current invocations are unchanged; the new function wraps it rather than replacing it.

The cache sits *below* the env var deliberately: a user who pinned `MMCLI_DATASETS` for an
air-gapped or reproducible setup must never be overridden by a cached copy.

Verify the recorded sha256 on **cache hits**, not only on download. The cache lives under a
path an attacker with write access to `XDG_CACHE_HOME` — or a second process — can plant
files in, and re-hashing 54 MB costs tens of milliseconds against a download that costs
seconds. Files resolved through `MMCLI_DATASETS` are deliberately *not* digest-checked: that
directory is explicitly user-managed and may legitimately hold a locally prepared dataset.
Say so in the docstring, because the asymmetry looks like an oversight otherwise.

  <behavior>
    - Happy path: downloads to the version cache, returns the path, second call issues no request
    - Truncated body (Content-Length longer than the bytes served): raises, cache left empty
    - Wrong digest: raises naming expected and actual digest, cache left empty, temp file removed
    - `MMCLI_DATASETS` set: raises without issuing any request, message naming the variable
    - Non-HTTPS URL: refused before any request
    - Redirect to a different host: refused, not followed silently
    - HTTP 404: raises naming the pinned version and the exact URL tried
    - Body longer than the registry `bytes` by more than a small tolerance: aborted mid-stream
  </behavior>
  <action>
Implement `fetch_dataset(name, *, force=False) -> str` using stdlib `urllib.request`. Adding
`requests` to shrink a binary would be self-defeating, and this is the one place that
temptation appears.

Each requirement below is a real failure mode, not ceremony:

- Download to a temp file **in the destination directory**, hash while streaming, verify, then
  `os.replace()`. Same-directory keeps the rename atomic; a partial file at the final path
  would become a poisoned cache hit on the next run, and the next run has no way to tell.
- Checksum mismatch: unlink the temp file and raise reporting expected and actual digests plus
  the URL. Never leave the bytes on disk "for debugging" — that is how a poisoned cache is
  created by a helpful hand.
- Reject non-HTTPS URLs outright. Surface cross-host redirects as an error rather than
  following them; the digest would catch substituted content, but an unexplained redirect is
  worth seeing.
- Abort if the streamed length exceeds the registry `bytes` by more than a small tolerance, so
  a hostile or misconfigured server cannot fill the disk before the digest check runs.
- Apply a connect and read timeout so a hung server fails rather than stalling forever.
- `tqdm` progress only when stderr is a TTY, so CI logs stay clean. Plan 10-06 reuses this
  same predicate to decide whether `init` may auto-fetch at all — keep it in one helper.
- **Never fetch when `MMCLI_DATASETS` is set**, even on an explicit call (REQ-DATA-03). That
  variable signals a managed environment; a tool that fetches anyway has silently defeated the
  air-gap. Raise with a message that names the variable and its current value.
- A 404 must name the pinned version and the full URL tried. TI reorganising paths is the most
  likely future breakage, so the error has to point straight at it rather than at the user.

Test against a local `http.server` fixture serving controllable bodies — not against TI. A
unit suite that hits the network is a unit suite that fails on a train.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| software-dl.ti.com → local disk | untrusted remote bytes are written to a path mmcli later extracts and trains on |
| cache directory → extraction | files under `XDG_CACHE_HOME` may be writable by other processes or users |
| dataset name → URL path | a name reaching `dataset_url` must not be able to steer the request |
| zip archive → project directory | archive member names control where files land |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-02-01 | Tampering | `fetch_dataset` network read | mitigate | HTTPS only, sha256 verified against the registry before `os.replace`, cross-host redirects refused |
| T-10-02-02 | Tampering | cache entry poisoning via partial write | mitigate | download to temp file in the destination directory, verify, then atomic `os.replace`; unlink temp on any failure |
| T-10-02-03 | Tampering | cache entry planted by another process/user | mitigate | verify sha256 on cache hits as well as on download; create cache dir mode 0700 |
| T-10-02-04 | Spoofing | dataset name interpolated into the URL path | mitigate | `dataset_url` resolves through `DATASET_REGISTRY` and raises on unknown names; no user-supplied URLs anywhere |
| T-10-02-05 | Denial of service | oversized or hung response | mitigate | abort when streamed length exceeds registry `bytes` + tolerance; connect and read timeouts |
| T-10-02-06 | Elevation of privilege | zip-slip when extracting a fetched archive | mitigate | confirm `extract_dataset()` rejects absolute and `..` member paths; add a test if it does not already have one |
| T-10-02-07 | Repudiation | silent air-gap defeat | mitigate | `MMCLI_DATASETS` set raises before any socket is opened, on every path, with a test asserting zero requests |
| T-10-02-SC | Tampering | npm/pip/cargo installs | accept | no new package-manager installs: `urllib.request` and `hashlib` are stdlib and `tqdm` is already a declared dependency, so no package legitimacy gate applies |

## Risks

- **Reachability.** Any remote source is unreachable for some corporate or air-gapped users.
  `MMCLI_DATASETS` is the escape hatch and must be tested, not merely documented.
- **Upstream path changes.** Availability depends on `software-dl.ti.com`. Two URL shapes
  already coexist, so TI has reorganised at least once. Pinning the versioned form and keeping
  sha256 verification limits the blast radius.
- **Digest drift.** If TI replaces a file in place, verification fails loudly rather than
  installing unexpected data — the intended behaviour, but it presents as a hard error, so the
  message must make the cause obvious and point at `docs/RELEASING.md` (written in 10-07).
