# Plan 10-02: Registry Versioning, Cache Layer, `mmcli datasets pull`

## Objective

Let datasets be fetched from TI's download server on demand, pinned to a TI engine version,
and cached — so the binary no longer carries them and a dataset can be release-specific.

Decisions D-1 through D-4 are resolved (see `10-RESEARCH.md`), so this plan is unblocked.

## Background

`mmcli/datasets.py` already has the seam:

```python
def _datasets_dir() -> str:
    env = os.environ.get("MMCLI_DATASETS")
    if env and os.path.isdir(env):
        return env
    return os.path.join(os.path.dirname(__file__), "example_datasets")
```

`DATASET_REGISTRY` holds one record per dataset (`filename`, `task_types`, `module`,
`description`); `extract_dataset()` is the only place a zip is opened. There is no download
path today.

The change is additive — `MMCLI_DATASETS` and the bundled directory keep their existing
precedence, so nothing regresses for managed environments.

**Versioning (D-1/D-3/D-4).** Datasets are fetched from TI, which already version-paths
them:

```
https://software-dl.ti.com/C2000/esd/mcu_ai/01_03_00/datasets/fan_blade_fault_dsi.zip
```

Five local names differ from TI's, so each entry carries both `filename` (local/cache name)
and `ti_name`. A module-level `DATASETS_DEFAULT_VERSION` supplies the version; an entry may
override with `ti_version`. `generic_audio_classification.zip` is locally authored, has no
`ti_name`, and stays bundled.

## Tasks

### Task 1: Registry gains ti_name/ti_version/sha256, URL is derived

<read_first>
- mmcli/datasets.py (`DATASET_REGISTRY`, all 10 entries)
</read_first>

<action>
Add module constants:

```python
TI_DATASETS_BASE = "https://software-dl.ti.com/C2000/esd/mcu_ai"
DATASETS_DEFAULT_VERSION = "01_03_00"    # TI engine version the URLs are pinned to
```

Add three optional per-entry keys: `ti_name` (TI's filename, when it differs),
`ti_version` (override), and `sha256` (required whenever `ti_name` is present).

Derive the URL rather than storing it — a hand-written URL per entry is nine places to get
the version wrong:

```python
def dataset_url(name: str) -> str | None:
    e = DATASET_REGISTRY[name]
    ti = e.get("ti_name")
    if ti is None:
        return None                      # locally authored, bundled only
    ver = e.get("ti_version", DATASETS_DEFAULT_VERSION)
    return f"{TI_DATASETS_BASE}/{ver}/datasets/{ti}"
```

Enforce at import that every entry with a `ti_name` has a `sha256`. A fetchable dataset
without a digest is a configuration error, and failing at import surfaces it where it is
cheap to see rather than mid-download. The ten digests are recorded in `10-RESEARCH.md`.

Use the **version-pathed** form, not the flat one. Both work, but the flat path is
effectively "latest" and can change under you; a versioned path is the closest thing TI
offers to immutability.
</action>

<verify>
<automated>
pytest tests/test_datasets_download.py -k "registry" -q
</automated>
Asserts: every entry with a `ti_name` has sha256; `dataset_url()` uses the default version;
`ti_version` overrides it; a `ti_name` entry missing sha256 raises at import;
`dataset_url('generic_audio_classification')` returns None.
</verify>

### Task 2: Version-scoped cache and resolution order

<read_first>
- mmcli/datasets.py (`_datasets_dir`, `extract_dataset`)
</read_first>

<action>
Add `_cache_dir(version)` returning `~/.cache/mmcli/datasets/<version>` (honour
`XDG_CACHE_HOME`), created lazily.

**The version must be part of the path.** A flat cache would let a version bump silently
reuse a dataset from an older TI release — the exact failure D-3 exists to prevent.

Resolution order becomes:

1. `MMCLI_DATASETS`
2. bundled `example_datasets/` (after 10-03: only `generic_audio_classification.zip`)
3. `~/.cache/mmcli/datasets/<version>/`
4. download

The cache sits *below* the env var deliberately: a user who pinned `MMCLI_DATASETS` for an
air-gapped or reproducible setup must never be overridden by a cached copy.
</action>

<verify>
<automated>
pytest tests/test_datasets_download.py -k "resolution or cache_key" -q
</automated>
Asserts: env var wins over bundled and cache; cache path contains the version; two versions
cache independently.
</verify>

### Task 3: Download with mandatory verification

<read_first>
- mmcli/datasets.py
- mmcli/cli.py (progress conventions — `tqdm` is already a declared dependency)
</read_first>

<action>
Implement `fetch_dataset(name, *, force=False) -> str`.

Each requirement below is a real failure mode, not ceremony:

- Download to a temp file **in the same directory**, verify sha256, then `os.replace()`.
  Same-directory keeps the rename atomic; a partial file at the final path would become a
  poisoned cache hit on the next run.
- Checksum mismatch: delete the temp file, raise reporting expected and actual digests.
- Reject non-HTTPS URLs. Surface cross-host redirects rather than following silently.
- `tqdm` progress only when stderr is a TTY, so CI logs stay clean.
- **Never auto-download when `MMCLI_DATASETS` is set** — that variable signals a managed
  environment (REQ-DATA-03).
- A 404 must name the version and the TI URL tried. TI reorganising paths is the most likely
  future breakage, so the error has to point straight at it.

Use stdlib `urllib.request`. Adding `requests` to shrink a binary is self-defeating.
</action>

<verify>
<automated>
pytest tests/test_datasets_download.py -k "fetch" -q
</automated>
Against a local HTTP server: happy path caches and returns the path; truncated body raises
and leaves the cache empty; wrong digest raises and leaves the cache empty; warm cache issues
no request; `MMCLI_DATASETS` set issues no request; non-HTTPS URL is refused.
</verify>

## Success Criteria

- `mmcli datasets pull <name>` fetches from the version-pinned TI URL, verifies sha256,
  caches under the version, and a second call performs no network request
- Corrupt, truncated, or wrong-digest downloads fail loudly and leave no cache entry
- `MMCLI_DATASETS` set ⇒ zero network calls in every path
- `datasets list --format json` is stable and machine-parseable

## Risks

- **Reachability.** Any remote source is unreachable for some corporate/air-gapped users.
  `MMCLI_DATASETS` is the escape hatch and must be tested, not merely documented.
- **Upstream path changes.** Availability depends on `software-dl.ti.com`. Two URL shapes
  already coexist, so TI has reorganised at least once. Pinning the versioned form and
  keeping sha256 verification limits the blast radius; `MMCLI_DATASETS` is the escape hatch.
- **Digest drift.** If TI replaces a file in place, verification fails loudly rather than
  installing unexpected data — the intended behaviour, but it will present as a hard error
  and the message must make the cause obvious.
