## Background: what already exists underneath

Waves 1–3 shipped the CLI surface this plan drives. `mmcli datasets list --format json`
emits `{"datasets": [{name, version, state, bytes, task_types, module, description}, …]}`
for all ten datasets; the committed contract is in `10-06-SUMMARY.md` and is authoritative.
`state` is one of exactly `bundled`, `cached`, `downloadable`, `unavailable`, computed live
against this machine rather than stored in the registry.

`unavailable` is the state that is easiest to get wrong, and the design spec is explicit that
it is not merely an error. It covers two genuinely different situations:

1. `generic_audio_classification` has no upstream source at all — it exists only inside the
   package and can never be fetched, on any machine.
2. **Any** dataset becomes `unavailable` when `MMCLI_DATASETS` is set to a directory that
   does not contain it, because that variable disables fetching outright (REQ-DATA-03). The
   dataset has a perfectly good upstream; this environment has opted out of using it.

A Download button in either case is a button that cannot succeed. The library must explain
instead of offering. The app can tell the two apart without any new CLI surface: the JSON's
`version` field is `null` exactly for the entry with no upstream, and `MMCLI_DATASETS` is
readable from the app's own child environment.

**Never pass `--fetch`.** Decision D-5 makes mmcli auto-fetch only when stderr is a TTY.
`ProcessRunner` always pipes stderr, so every invocation from this app is non-interactive by
construction and the app owns all prompting. `--fetch` would re-create precisely the silent
multi-megabyte transfer REQ-UX-01 exists to prevent, and would make this plan's affordances
decorative.

## Decision: removal goes through mmcli, not through the app

REQ-UX-02 requires removal and no removal command exists. Two options were considered.

**Rejected — the app deletes the file at `mmcli datasets path <name>`.** It is fewer moving
parts, and it is wrong for four reasons. `datasets path` is a *resolution* query, not a cache
query: for a `bundled` dataset it returns the path inside the packaged directory or inside
the user's `MMCLI_DATASETS` directory, so an app that unlinks whatever that command prints
will one day delete packaged program data or a user's air-gapped dataset store. Guarding on
`state == cached` does not close that, because state and path come from two separate
subprocess invocations and the environment can differ between them. Second, the cache layout
is version-scoped (`<cache-home>/mmcli/datasets/<version>/`) and keyed off a per-entry
version pin; an app that deletes into it has quietly taken a dependency on a layout it does
not model and cannot be tested against. Third, it hands unlink authority to a GUI over a path
parsed out of subprocess stdout — a tampering surface for no benefit. Fourth, every other
dataset operation in this system goes through mmcli, and headless and CI users would still
have no way to remove a dataset.

**Chosen — add `mmcli datasets remove <name>` and have the app call it.** mmcli already owns
the registry, the cache layout, the version keying and the resolution precedence, so the
guard that "this path is inside the version-scoped cache directory and nowhere else" is
written once, in Python, under pytest, and is shared by the app and by anyone at a terminal.
The app gains no new knowledge of the cache and no new authority over the filesystem: it
runs a subprocess and re-reads the catalog, exactly as it does for `pull`. The cost is one
small subcommand in a file this phase has already been editing.

  <action>
Add `cache_entry_path(name)` to `mmcli/datasets.py`: a public helper returning the
version-scoped cache path for a dataset (`_cache_dir(version)/filename`) regardless of
whether the file is present. This is deliberately *not* `_resolve_dataset_zip` — it answers
"where would the cache entry be", never "where does this dataset currently resolve from".
Keeping the two questions separate in the source is the whole safety argument for removal.

Add `mmcli datasets remove <name>` in `mmcli/cli.py`:

- Unknown name: stderr message listing every registered name, exit 2 — same shape as `pull`
  and `path`, so the app needs no special case.
- Compute the target with `cache_entry_path(name)` and assert, immediately before unlinking,
  that the target's directory equals `_cache_dir(version)` for that entry. This guard is not
  redundant with how the path was computed; it is the assertion that survives a future
  refactor of the path computation. If it does not hold, refuse and exit 1.
- File absent: print that the dataset is not cached and there is nothing to remove, exit 0.
  Removal is idempotent — the app calls this after the user presses a button and must not
  have to distinguish "already gone" from "failed".
- File present: unlink it, print the removed path and the bytes freed, exit 0.
- `OSError` on unlink: `ERROR: ` message naming the path, exit 1.
- Never recurse, never remove a directory, and do not sweep other versions' copies. A stale
  entry under an older version pin belongs to whatever engine version pinned it; deleting it
  from here would be removing data this invocation knows nothing about.
- Do not refuse when `MMCLI_DATASETS` is set. Removing a cache entry in that environment is
  harmless — the cache is not what resolves there — so print one informational line saying
  the removal does not change what resolves in this environment, and proceed. A refusal here
  would be a policy branch the app then has to model for no gain.

Add the `remove` line to the `datasets` subparser description alongside `list`/`pull`/`path`,
and to its Examples block.

Then fix the disk-space gap in `_download_to_cache`. Today an `ENOSPC` from `out.write(chunk)`
escapes as a bare `OSError`, which `_handle_datasets_pull` does not catch (it catches only
`KeyError` and `RuntimeError`) — so a full disk produces a Python traceback. Wrap the write
loop and translate `OSError` into `RuntimeError`, naming the cache directory, and when
`errno` is `ENOSPC` say plainly that there is not enough free space rather than echoing the
raw errno string. The existing `except BaseException` cleanup already removes the temp file,
so no partial download is left behind; keep that behaviour intact. Without this fix the
"no disk space" branch required by the design spec's failure-mode rule is unreachable, and
Task 2's classifier would be classifying a message that can never arrive.

source emits:

- integrity — `Checksum mismatch for`, `Truncated download of`, and the `Content-Length …
  exceeds the registry size` refusal. All three mean bytes arrived and were wrong, which is
  a categorically different event from bytes not arriving.
- offline — `Failed to fetch '<name>' from <url>:` , which is where urllib's connection and
  timeout failures land.
- out-of-space — the wording Task 1 introduced.
- refusal — `Refusing to fetch '<name>': MMCLI_DATASETS is set` and `has no upstream source`.
  These are policy outcomes, not faults, and must not be styled as errors.
- unrecognised — everything else, including HTTP status failures.

**Every case carries mmcli's verbatim message.** Classification selects which remedy sentence
to show; it never replaces the text. That way a future mmcli message this classifier has
never seen degrades to "unrecognised, here is what mmcli said" rather than to a confident
wrong diagnosis — which is exactly the failure the checksum-shown-as-network-error rule in
the design spec is about.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| mmcli stdout → app JSON decoder | subprocess output is parsed and drives UI state and button availability |
| user selection → subprocess argv | a dataset name chosen in a list becomes an argv element |
| app button press → filesystem deletion | a GUI action results in a file being unlinked |
| network transfer initiated from a GUI | bytes arrive from an upstream host and land in a cache directory |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-09-01 | Tampering | `datasets remove` target path | mitigate | removal is computed from `cache_entry_path()` and re-asserted to sit inside `_cache_dir(version)` immediately before unlink; never derived from `_resolve_dataset_zip`, never recursive, never a directory (Task 1, Task 4 step 9) |
| T-10-09-02 | Denial of service | user data deleted by the app | mitigate | the app holds no unlink authority at all; it runs a subcommand whose blast radius is bounded and tested in pytest |
| T-10-09-03 | Elevation of privilege | dataset name reaching a subprocess | mitigate | argv is passed as an array through `ProcessRunner` (no shell string), and only names that came back from mmcli's own list are ever sent |
| T-10-09-04 | Spoofing | substituted bytes from upstream | mitigate | unchanged from 10-02: sha256 verified before the atomic rename, temp file removed on any failure; this plan adds only that the failure is *classified as integrity* and never rendered as a network problem |
| T-10-09-05 | Repudiation | a misclassified failure hides what happened | mitigate | classification selects a remedy sentence only; mmcli's verbatim message is always displayed, and an unrecognised message degrades to "unrecognised" rather than to a confident wrong diagnosis |
| T-10-09-06 | Denial of service | unauthorised background transfer | mitigate | transfers start only on an explicit button press; `--fetch` is never passed, so D-5's non-TTY rule keeps mmcli from fetching underneath the app |

## Notes

Task 1 lands in a different repository from Tasks 2–3 and is a natural resume point if

Two places where the approved design spec is thinner than the implementation needs, recorded
here rather than diverged from silently:

- The spec says "the cache location comes from `mmcli datasets path`". It does not. That
  command resolves a *dataset*, returning the packaged path for a bundled one and exiting
  non-zero for anything not yet local — so on a fresh machine it cannot report the cache
  directory at all. This plan takes the cache location from the path returned when removing
  or after downloading, and shows nothing rather than guessing when nothing is cached.
- The spec's affordance table gives Remove only to `cached`. A dataset can be `bundled`
  *and* still have a cache entry from an earlier download — the packaged copy simply wins
  resolution — and that disk space is then unreclaimable from the library. This plan
  implements the table as approved; `mmcli datasets remove` handles the shadowed case from a
  terminal. Worth revisiting if it bites.
