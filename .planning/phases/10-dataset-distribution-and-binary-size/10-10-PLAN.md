## Background

### The defect

`pyproject.toml:22-23`:

```toml
[tool.setuptools.package-data]
mmcli = ["example_datasets/*.zip", "data/*.yaml"]
```

`pip wheel --no-deps .` produces a 108.2 MB wheel containing all ten dataset zips —
`fan_blade_fault` 54.0 MB, `mnist_image_classification` 44.8 MB, `arc_fault_classification`
12.7 MB, and the rest. This is the same defect 10-03 fixed for PyInstaller, in a channel that
plan never looked at.

10-03's fix (D-2) was an explicit `BUNDLED_DATASETS` allowlist naming exactly
`generic_audio_classification.zip`, staged into a temp dir and `--add-data`'d, so that *what a
build ships is a property of the build script, not of the developer's working tree*. This plan
applies the identical reasoning to `package-data`: one literal filename, no wildcard.

`generic_audio_classification.zip` (18,371 bytes) is the right and only one to keep: it is
locally authored (commit `be06559`), it has **no `ti_name`** in `DATASET_REGISTRY`, it is
deliberately absent from the mirror release, and `fetch_dataset()` refuses to fetch it. If it
does not ship in the wheel, it is unreachable for a pip user. The nine all carry a `ti_name`, a
`sha256` and a live mirror asset.

### Why a working-tree precondition, not just a diff (measured, load-bearing)

```
$ git ls-files mmcli/example_datasets
mmcli/example_datasets/.gitkeep
mmcli/example_datasets/generic_audio_classification.zip

$ git check-ignore -v mmcli/example_datasets/fan_blade_fault.zip
.gitignore:10:mmcli/example_datasets/*.zip	mmcli/example_datasets/fan_blade_fault.zip
```

**Only one zip is tracked in git.** The nine live in the maintainer's working tree and on the
mirror release; `.gitignore:10` ignores them. Three consequences that shape this plan:

1. A fresh clone builds a small wheel *regardless of the glob*. The 108.2 MB wheel is a property
   of the tree that cuts releases — which is precisely the dangerous case, and precisely the
   failure mode 10-03 named.
2. **Any verification that builds a wheel in a tree missing the nine is vacuous.** Task 2 asserts
   the precondition before it measures anything.
3. **A CI wheel-size gate would not catch this regression** (see Notes for 10-08): CI's checkout
   contains one zip, so a re-added wildcard would still produce a small wheel there. The guard
   has to be source-level. This is not a convenience choice — an artifact-level gate is the
   weaker check here, the opposite of the usual tradeoff.

### The sdist question, settled empirically

Setuptools' `sdist` derives package data from `package-data` — it is not wheel-only. Measured on
a scratch project with the same `pyproject.toml` shape (setuptools 82.0.0, four dummy zips, glob
narrowed to the single literal filename):

```
=== SDIST ===  mmcli/data/x.yaml
               mmcli/example_datasets/generic_audio_classification.zip
=== WHEEL ===  mmcli/data/x.yaml
               mmcli/example_datasets/generic_audio_classification.zip
```

Both artifacts followed the narrowed glob. There is **no `MANIFEST.in` in this repo**
(`ls MANIFEST.in` → no such file), no `setup.py` and no `setup.cfg`, so nothing else re-includes
the zips. `MANIFEST.in` is therefore deliberately **not** in `files_modified` and must not be
created pre-emptively — an unnecessary `MANIFEST.in` is a second place packaging rules live, and
this phase spent a review (F-1) collapsing exactly that class of duplication. Task 2 still
measures the real sdist rather than trusting the scratch result; the contingency if it disagrees
is written into that task.

### `_dataset_state()` needs no change (checked, not assumed)

`mmcli/cli.py:1438-1467`: `_dataset_state()` returns `bundled` when `_resolve_dataset_zip()`
lands in `_datasets_dir()`, and when it resolves nothing, returns `downloadable` iff the registry
entry has a `ti_name` and `MMCLI_DATASETS` is unset. With the nine absent from the installed
package directory, the nine become `downloadable` and the audio zip stays `bundled` — the exact
runtime shape the PyInstaller binary already has (10-03 verified it there). No code change is
required. Task 2 verifies this against a real installed wheel anyway rather than reasoning about
it, because that is the whole acceptance question for a pip user.

## Notes for other plans — flagged, not edited

**For 10-08 (CI gates, wave 4, not yet executed).** Two things, one of which is a correction to

   workflows, so this plan's guard reaches CI with **no edit to 10-08 at all**. That is the main
   reason the guard lives in that file (see the tradeoff below).
2. **Do not add a "build a wheel in CI and check its size" gate on the assumption it would catch
   this.** It would not. `.gitignore:10` ignores `mmcli/example_datasets/*.zip` and `git ls-files`
   shows only `generic_audio_classification.zip` tracked, so a CI checkout contains one zip and
   would build a small wheel even with the wildcard restored — a green gate over a real
   regression, which is worse than no gate. A meaningful artifact-level wheel gate would first
   have to seed the nine into the checkout (from the `datasets-01_03_00` mirror release), which is
   a ~131 MB download per run. If 10-08 wants it anyway, that cost and that seeding step are the
   decision to make explicitly; the source-level guard is the cheap check that actually works
   here.

**For 10-07 (`docs/RELEASING.md`, wave 5).** There is no PyPI publish job in either workflow
today (`grep -rn "pypi\|twine" .github/workflows/` → nothing), so `pip install mmcli` currently
means installing from source or a git URL — which still builds the wheel locally and still

to state, extended to the pip channel.

## The guard decision and its tradeoff

**Chosen: a source-level test that parses `pyproject.toml`, added to the existing
`tests/test_build_config.py`, not a new file and not a build-and-measure test.**

- *Against a build-and-measure test:* it needs `build`/`pip`, network for build isolation, and
  tens of seconds to minutes; and — decisively — **in CI it would be vacuous**, because the
  checkout does not contain the nine zips (see the 10-08 note). The stronger-but-slower option is
  here also the weaker option. That inverts the usual tradeoff and is the reason the choice is not
  merely about speed.
- *Against a new `tests/test_packaging_config.py`:* 10-08 Task 1 already wires
  `tests/test_build_config.py` into both workflows; a new file would need 10-08 edited, which this
  plan is explicitly not doing, and would leave the guard uncollected in CI until someone noticed.
  It would also need a second copy of `MIRRORED_DATASET_FILENAMES` — the exact duplication this
  file's own docstring and finding F-1 exist to prevent.
- *Cost accepted:* a text-parsing guard can be fooled by a `pyproject.toml` restructure it fails to
  parse. Mitigated by making `_package_data_patterns()` assert it found the section and the array,
  so an unparseable file is a loud failure rather than a vacuous pass, and by Task 2 measuring the
  real artifacts once at implementation time.
- *Parser choice:* regex over raw text rather than `tomllib`, because both workflows pin Python
  3.10 where `tomllib` is absent and neither installs `tomli`. Same call 10-08 made about PyYAML.

## Out of scope

- **`pytest.ini`'s `[tool:pytest]` header and `[tool.pytest.ini_options]` in `pyproject.toml`.**
  Known, deliberately untouched. Fixing the header activates 30+ never-run test files and a
  `--cov` that would fail every CI job on a missing `pytest-cov`. This plan edits
  `pyproject.toml` only in the `[tool.setuptools.package-data]` block, so it does not interact
  with either pytest config; the guard reads the file as text and asserts nothing about them.
- **Deleting any dataset zip from the working tree.** All ten stay. REQ-DATA-04 and the mirror's
  provenance both depend on it.
- **Publishing to PyPI, or adding a publish job.** No such job exists; creating one is a decision,
  not a side effect of a packaging fix.
- **`scripts/binary_size_ceiling.txt` and REQ-SIZE-01's open 31.84 MB / 15 MB question.** That is
  about `dist/mmcli`; this plan is about the wheel and sdist and introduces no second ceiling file.
