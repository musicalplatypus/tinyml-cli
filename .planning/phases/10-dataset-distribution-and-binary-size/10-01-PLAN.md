## Background

`build_macos.sh` documents the intent at line 4:

```
# The binary is lightweight (~10 MB) because tinyml_modelmaker is NOT bundled.
```

Nothing enforced it. The generated `mmcli.spec` had `excludes=[]`, so PyInstaller's static
analysis followed three guarded probes and bundled their whole dependency trees:

| Site | Statement | Guarded by |
|------|-----------|------------|
| `mmcli/recommend.py:121` | `import tinyml_modelmaker` | `try/except ImportError: pass` |
| `mmcli/diagnose.py:131` | `import tinyml_modelmaker` | `try/except ImportError` |
| `mmcli/diagnose.py:208` | `import tvm` | `try/except ImportError` |

PyInstaller does not care that they are guarded — a reachable `import` is followed. The
other `import tinyml_modelmaker` occurrences (`info.py:40`, `compare.py:30`, `cli.py:218`)
are inside *string literals* sent to a subprocess, so they were never the problem.

Because all three real sites already handle `ImportError`, excluding the modules is
behaviour-preserving: the probes become the no-ops their `except` branches already expect.

Measured effect: 260.3 MB → 138.7 MB, startup ~6.2 s → ~5.2 s (3-run steady state).

**`numpy` and `pandas` must NOT be excluded** — `analyze.py::_row_count` imports them to
compute dataset statistics, and excluding them breaks `mmcli analyze`.

### There are three build scripts, not two

`.github/workflows/release.yml` builds and publishes three artifacts per release:
`build_linux.sh` (line 95), `build_windows.ps1` (line 99), `build_macos.sh` (line 103). Only
`build_macos.sh` carries the exclusions today (commit `143dd7e`). The three guarded probes
above are equally reachable on Windows and Linux, so those two artifacts still bundle the
engine. Any plan that fixes "the build" and means two of three scripts leaves REQ-SIZE-02
failing for a third of the users who download a release.

`build_windows.ps1` also carries the same stale `~10 MB` comment at line 3 — the identical
false claim, in the identical position, on the platform nobody measured.

  <action>
Create `scripts/pyinstaller_excludes.txt`: one module name per line, no comments, no blank
lines, holding exactly the thirteen names from Task 1. Then make all three build scripts read
it instead of carrying their own copy.

The shared file is not a stylistic preference here — it is the only structure that survives
three scripts. A list maintained in three places will diverge, and divergence between build
scripts is invisible until a user on the odd platform reports a 260 MB download. Sharing also
lets `tests/test_build_config.py` assert "each script excludes everything in the list" rather
than "these three hand-maintained lists happen to be equal".

- **bash** (`build_macos.sh`, `build_linux.sh`): read the file into the flag array, e.g.
  iterate lines and append `--exclude-module "$m"` for each. Replace the inline `EXCLUDES=()`
  array in `build_macos.sh` with the file read; keep the explanatory comment, which now points
  at the shared file.
- **PowerShell** (`build_windows.ps1`): the bash idiom does not transfer. Build a `[string[]]`
  array with `Get-Content`, e.g. `$ExcludeArgs = Get-Content $ExcludeFile | ForEach-Object {
  '--exclude-module', $_ }`, then splat it into the invocation with `@ExcludeArgs`. Do **not**
  interpolate the array into the existing backtick-continued command line — PowerShell
  stringifies an array into a single space-joined argument there, which PyInstaller receives as
  one malformed flag. Resolve the path relative to `$ScriptDir`, matching how the script
  already resolves `build` and `dist`. Use `Join-Path` rather than string concatenation with
  `\`, so the script does not break under a PowerShell Core host.

Do not change anything else about the Windows or Linux invocations in this task. They differ
from macOS in other ways (`--paths`, `--collect-submodules`, `--add-data`); 10-03 Task 2 deals
with the `--add-data` divergence, and the rest is out of scope.

If a script genuinely cannot read the shared file, duplicate the list there and say so in the
summary — Task 3's test asserts every script against the shared file either way, so a
one-sided edit still fails.
  </action>
