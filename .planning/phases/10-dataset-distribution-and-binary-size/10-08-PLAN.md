inherited rather than made here, and so REQ-SIZE-01's satisfaction is attributable.

Two consequences for the gates: the 8 s startup bound was measured on a developer laptop and

## Background

Both workflows run the same command:

```
python -m pytest tests/test_cli_integration.py tests/test_tier4_cli.py -v --tb=short -k "not TestInitDatasetExtractReal"
```

- `.github/workflows/test-cli.yml:55` — the Tier 4 job, on push and PR
- `.github/workflows/release.yml:58` — the pre-build gate, on tag

Passing explicit paths means pytest collects **only** those two files. Three new test files
land in this phase and none of them would ever run in CI:

| File | From | What stops being enforced without it |
|------|------|--------------------------------------|
| `tests/test_build_config.py` | 10-01 Task 3 | removing an `--exclude-module` from any build script, or loosening the size ceiling |
| `tests/test_datasets_download.py` | 10-02 | `MMCLI_DATASETS` air-gap enforcement, sha256 verification, atomic replace |
| `tests/test_datasets_cli.py` | 10-06 | the D-5 auto-fetch policy and the `datasets list --format json` contract 10-04 parses |

### Why the explicit file list stays (checked, not assumed)

The obvious move is to replace the file list with a bare `python -m pytest` and let
`pytest.ini` decide. That is wrong here, for two measured reasons:

1. **`pytest.ini` is inert.** It declares `[tool:pytest]`, which is the section name pytest
   reads from `setup.cfg`, not from `pytest.ini` — where the section must be `[pytest]`. So
   `testpaths = tests` and the `--cov` `addopts` are not applied at all. Running bare
   `python -m pytest` from the repo root collects `test_sigsegv.py` at the repo root, outside
   `tests/`, which confirms `testpaths` is not in effect. Verified 2026-07-22.
2. **Thirty-plus test files have never run in CI.** Switching to broad collection would enable
   all of them in one change, on three operating systems, inside the job that gates releases.
   The existing `-k "not TestInitDatasetExtractReal"` deselection is evidence that exclusions
   here are deliberate, so the safe reading is that the narrow list is intentional.

Fixing `pytest.ini`'s section header and auditing the other thirty files are both real and
both out of scope: either one is a phase of its own, and neither is needed for REQ-SIZE-02.
Record the `pytest.ini` finding so the next person does not "fix" the header casually and
silently turn on `--cov` (pytest-cov is not installed in either workflow, so bare
`--cov=mmcli` in `addopts` would make every job fail on an unrecognised argument).

So: append the three files to the existing list, keep the deselection, and add a test that
makes "someone added a test file and forgot CI" a failing build rather than an invisible gap.

### Why one plan owns `.github/workflows/`

Three plans in three different waves each produce one of these test files. If each wired its
own, the same two lines would be edited three times in three waves, and the two workflows would
have three chances to end up with different lists. Single ownership makes the wiring one edit,
and `tests/test_ci_workflows.py` makes divergence a test failure rather than a discovery. This
is the same argument that put the exclude list in one shared file in 10-01.

Add two steps to the `build` job, after "Verify binary" and before "Upload artifact", both with
`shell: bash` so they run identically on all three runners (the Windows runner's bash is Git
Bash, which has GNU coreutils).

**Step A — size gate.** Read the ceiling from `scripts/binary_size_ceiling.txt` and fail if the
built artifact exceeds it. Read it from the file, never as a literal in the YAML: a number in
the workflow is a fourth copy of a number this phase spent a whole review finding (F-1)
reducing to one. Use `wc -c < "$BINARY"` for the size — `stat -f%z` is BSD-only and `stat -c%s`
is GNU-only, and `wc -c` is the same everywhere, which matters when the same step runs on three
operating systems. Print the actual size and the ceiling on both success and failure, so a
failure is diagnosable from the log without a re-run.

This step is the only place the real size of the Linux and Windows artifacts is ever known.
`tests/test_build_config.py` asserts the build *scripts* at the source level; nothing before
this measures what those scripts actually produce on a platform no maintainer builds locally.
That is why 10-01 and 10-03 defer their Linux and Windows size claims here.

**Step B — empty-bundle probe.** Run
`"${{ matrix.binary }}" datasets path generic_audio_classification` and fail if it exits
non-zero. This is the runtime check that the staged `--add-data` from 10-03 Task 2 actually
landed inside this platform's binary. It exists because PyInstaller accepts a wrong `--add-data`
separator without complaint: the POSIX `src:dst` form on Windows produces a binary with an
empty bundle and a successful build. `--version` still passes on such a binary, so the existing
"Verify binary" step cannot see it; the first symptom would be a user's `init --dataset` failing
after release.

Place both steps before "Upload artifact" so a failing build publishes nothing. Do not add
`continue-on-error` here — unlike the test job, the build job has no Windows tolerance today
and adding one would defeat the purpose of the gate.

Leave `.github/workflows/test-cli.yml` alone in this task; it builds no binary.
  </action>
