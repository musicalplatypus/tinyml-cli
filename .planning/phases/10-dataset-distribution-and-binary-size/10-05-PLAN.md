# Plan 10-05: Documentation

## Objective

Update user-facing documentation for on-demand datasets, and write the release-process
document the versioning scheme depends on.

Runs last because it documents the interfaces settled by 10-02 (`datasets` subcommand),
10-03 (unbundling and asset publication) and 10-04 (the app's download affordance).

## Background

Three distinct gaps, only one of which is "missing docs".

**1. Existing documentation becomes factually wrong.** `README.md:736` states:

```
| `MMCLI_DATASETS` | bundled `example_datasets/` | Override directory containing example dataset zips |
```

After D-2 nothing is bundled, so both the stated default and the word "Override" are wrong.
`README.md:507` shows `export MMCLI_DATASETS=...` without explaining that it now also
disables fetching. Wrong documentation is worse than none — this is the same failure as the
`build_macos.sh` "~10 MB" comment that masked the bloat for so long.

**2. `README_zh.md` mentions `MMCLI_DATASETS` twice** and will silently drift out of sync
with the English README.

**3. There is no release-process document at all**, and D-3 places obligations on whoever
cuts a release: upload the assets, bump `DATASETS_DEFAULT_TAG`, never replace a published
asset. If those obligations live only in a plan file, the scheme rots the first time someone
else cuts a release — and the failure mode is silent (a stale tag serving old data), not a
crash.

Sphinx already autodocs `mmcli.datasets` (`docs/mmcli.rst:39-42`), so new public functions
appear automatically provided their docstrings are written.

### Task 3: Write docs/RELEASING.md

<read_first>
- mmcli/datasets.py (`DATASETS_DEFAULT_TAG`, per-entry `tag`, `sha256`)
- .planning/phases/10-dataset-distribution-and-binary-size/10-RESEARCH.md (D-1/D-2/D-3)
</read_first>

<action>
Create `docs/RELEASING.md` covering the dataset obligations of a release:

1. **Cutting a release** — bump `DATASETS_DEFAULT_TAG` to the new tag; upload any dataset
   that changed as an asset on that tag; leave unchanged datasets pinned to their existing
   tag via a per-entry `tag` override.
2. **Published assets are immutable.** Never replace an asset in place: clients cache by
   digest under the tag, so replacing one silently breaks every machine that already fetched
   it. Publish under a new tag instead.
3. **Adding a new dataset** — add the zip, upload it, record `sha256` (`shasum -a 256`), add
   the registry entry, and confirm `mmcli datasets pull <name>` works from a clean cache.
4. **Verification before announcing** — from a machine that has never built the repo:
   `rm -rf ~/.cache/mmcli/datasets && mmcli datasets pull <each>`.

Explain *why* for each rule. A rule whose reason is unstated gets "optimised away" by the
next person; the immutability rule in particular looks like pointless bureaucracy until you
know clients cache by digest.
</action>

## Notes

Documentation is a deliverable of this phase, not a postscript. The root cause of the bloat
was a comment asserting an invariant nothing enforced — `build_macos.sh:4` claimed "~10 MB"
for months while shipping 260 MB. Leaving the same class of stale claim in the README after
this change would repeat that mistake.
