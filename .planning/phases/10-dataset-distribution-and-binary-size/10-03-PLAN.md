# Plan 10-03: Publish Datasets as Release Assets, Unbundle Entirely

## Objective

Publish all ten dataset zips as assets on the `PlatypusCLI_*_Release` tags and stop bundling
any of them, taking the binary from ~138.7 MB to roughly 14 MB.

Per D-2, **nothing is bundled** — every dataset is fetched on demand or supplied via
`MMCLI_DATASETS`.

## Background

`--add-data mmcli/example_datasets:mmcli/example_datasets` currently bakes 125 MB into the
binary:

| Dataset | Size |
|---------|------|
| fan_blade_fault.zip | 54 MB |
| mnist_image_classification.zip | 45 MB |
| arc_fault_classification.zip | 13 MB |
| ecg_classification.zip | 4.4 MB |
| generic_timeseries_anomalydetection.zip | 4.0 MB |
| generic_timeseries_classification.zip | 2.5 MB |
| pir_detection.zip | 1.5 MB |
| generic_timeseries_regression.zip | 888 KB |
| *(2 further small zips)* | — |

`--onefile` extracts the whole archive on **every launch**, so this is paid per invocation,
not once at install — which is why startup tracks payload size so closely.

**These files are currently unbacked.** `.gitignore:10` excludes
`mmcli/example_datasets/*.zip`, so nine of the ten exist only on one developer machine and
are in no repository or release. Task 1 is therefore the first backup they have ever had,
and should be done before anything that touches the build.

## Tasks

### Task 1: Publish the assets and record digests

<read_first>
- mmcli/example_datasets/ (confirm all 10 zips are present locally before starting)
- mmcli/datasets.py (`DATASET_REGISTRY` — the `sha256`/`tag` fields added in 10-02)
</read_first>

<action>
Compute digests, then upload every zip as an asset on the target release tag:

```bash
cd mmcli/example_datasets
shasum -a 256 *.zip                       # record each digest
gh release upload PlatypusCLI_1.1.2_Release *.zip --repo musicalplatypus/tinyml-cli
```

Paste each digest into its `DATASET_REGISTRY` entry.

Treat published assets as **immutable**. If a dataset must change, publish it on a new tag
and set that entry's `tag` override — never replace an asset in place, because every cached
client keys on the digest and would break.

Verify the upload independently of your own machine's copies: download one asset fresh and
confirm its digest matches the registry.
</action>

<verify>
<automated>
gh release view PlatypusCLI_1.1.2_Release --repo musicalplatypus/tinyml-cli --json assets --jq '[.assets[].name | select(endswith(".zip"))] | length'
</automated>
Must print 10. Then, from a clean cache:
<automated>
rm -rf ~/.cache/mmcli/datasets && ./dist/mmcli datasets pull fan_blade_fault && ./dist/mmcli datasets path fan_blade_fault
</automated>
</verify>

## Success Criteria

- All 10 zips are assets on a release tag, digests recorded in the registry
- `dist/mmcli` ≤ 15 MB, startup < 2.5 s (3-run median)
- `mmcli init --dataset <any>` works from a clean cache with network
- With `MMCLI_DATASETS` set to a directory of the 10 zips, every `init --dataset` works with
  **zero** network access
- README and build-script comments state real numbers

## Rollback

Restoring the `--add-data` line reverts to a bundled binary. The registry `tag`/`sha256`
fields are inert when the file is already present locally, so rollback needs no code change —
worth stating plainly, because it makes this cheap to try and cheap to undo.
