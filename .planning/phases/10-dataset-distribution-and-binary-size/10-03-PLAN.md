# Plan 10-03: Unbundle the Large Datasets

## Objective

Stop shipping the two largest dataset zips inside the binary, taking it from ~138.7 MB to
roughly 40 MB.

**Blocked on the same human decision as 10-02** (hosting), plus a second: whether to keep
the 8 small datasets bundled (Option 2, ~40 MB) or unbundle everything (Option 3, ~14 MB).

## Background

`mmcli/example_datasets/` is 125 MB across 10 zips:

| Dataset | Size |
|---------|------|
| fan_blade_fault.zip | 54 MB |
| mnist_image_classification.zip | 45 MB |
| arc_fault_classification.zip | 13 MB |
| ecg_classification.zip | 4.4 MB |
| generic_timeseries_anomalydetection.zip | 4.0 MB |
| generic_timeseries_classification.zip | 2.5 MB |
| pir_detection.zip | 1.5 MB |
| generic_timeseries_regression.zip | 888 KB |
| *(2 further small zips)* | — |

The top two are 99 MB — 71% of the payload — and are the least likely to be the *first*
dataset a new user tries. The synthetic `generic_timeseries_*` sets are what most first runs
use and total only a few MB.

Because `--onefile` extracts the whole archive on every launch, this payload is paid on
every single invocation, not once at install. That is why startup improves so much.

## Tasks

### Task 1: Publish the large zips and record digests

<action>
Upload `fan_blade_fault.zip` and `mnist_image_classification.zip` to the agreed host.
Compute `shasum -a 256` for each and paste the digests into `DATASET_REGISTRY` alongside
their `url`.

Treat published zips as immutable. If a dataset needs to change, publish it under a new name
rather than replacing the file — every cached client keys on the digest.
</action>

<verify>
`mmcli datasets pull fan_blade_fault` succeeds from a clean cache on a machine that has
never built the repo.
</verify>

### Task 2: Narrow what the build bundles

<read_first>
- build_macos.sh (the `--add-data` line)
</read_first>

<action>
Replace the blanket `--add-data mmcli/example_datasets:mmcli/example_datasets` with a staged
directory containing only the datasets to be bundled, so the choice is explicit in the build
rather than implied by what happens to be on disk.

Drive it from a single list in the script (`BUNDLED_DATASETS=(...)`) and stage those files
into a temp dir passed to `--add-data`. A developer with extra zips in their working tree
must not accidentally ship them.
</action>

<verify>
`ls -la dist/mmcli` ≤ 45 MB. `mmcli init --dataset generic_timeseries_classification`
works with no network. `mmcli init --dataset fan_blade_fault` triggers a download.
</verify>

## Success Criteria

- `dist/mmcli` ≤ 45 MB, startup < 2.5 s (3-run median)
- All 10 datasets remain obtainable: bundled, cached, downloaded, or via `MMCLI_DATASETS`
- Offline machine + `MMCLI_DATASETS` ⇒ every `init --dataset` works, zero network
- README and build-script comments state real numbers

## Rollback

Restoring the blanket `--add-data` line reverts to a fully bundled binary. The registry
`url`/`sha256` fields are inert when the file is already present, so rollback needs no code
change — worth stating plainly, because it makes this cheap to try.
