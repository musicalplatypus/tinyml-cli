<objective>
The fetch-on-demand design shipped in 10-02/10-06 is non-functional in production: as of
2026-07-23 `software-dl.ti.com` 302-redirects every dataset path to `downloads.ti.com`, which
returns 404 for every version — TI reorganised paths, the exact risk 10-RESEARCH's D-1 flagged.
The registry digests are correct (all ten bundled zips were re-hashed and match), so we already
hold the authentic bytes.

This plan reverses D-1: instead of fetching from TI, it MIRRORS the nine fetchable datasets to
this project's own PUBLIC GitHub Release assets, repoints `fetch_dataset()` at that mirror
(including a narrow, deliberate relaxation of the cross-host redirect refusal so the one
GitHub-signed-asset hop is permitted while all other cross-host redirects stay refused),
verifies the whole mirror end to end through the real fetch path, and only THEN unbundles —
taking the binary from ~138 MB to <= 15 MB while keeping `generic_audio_classification.zip`
(the one locally-authored dataset, D-2) bundled on all three platforms.

Purpose: unbundling moves ~131 MB of the user's data supply off the binary and onto a network
path. That is only safe if the network path has been exercised end to end first, against the
real mirror, comparing content and not merely reachability. The mirror must exist and verify
before anything is deleted.
Output: repointed fetch machinery with a narrowed redirect rule, a published 9-asset release, a
re-runnable digest gate proving the mirror serves the registry bytes, an explicit bundling
allowlist in all three build scripts, the lowered size ceiling, and honest build-script comments.

Scope note (expected, not a violation): this plan edits `mmcli/datasets.py`, a file 10-02
"owns". Repointing the fetch source and relaxing the redirect handler cannot be done anywhere
else. This is called out here and must be noted in the SUMMARY.
</objective>

<design_decisions>
The four decisions the objective required be made explicitly. Executor implements these; do not
re-litigate.

D-A — Mirror URL scheme (asset naming):
  Assets are named by the LOCAL `filename` (what is on disk in mmcli/example_datasets/ and what
  the cache stores), NOT by `ti_name`. The upload step publishes the on-disk files verbatim, so
  asset name == filename == cache filename — one name end to end, no rename step. dataset_url
  composes {DATASETS_MIRROR_BASE}/{DATASETS_MIRROR_TAG_PREFIX}{version}/{meta['filename']} with
  DATASETS_MIRROR_BASE = "https://github.com/musicalplatypus/tinyml-cli/releases/download" and
  DATASETS_MIRROR_TAG_PREFIX = "datasets-".
  Example: fan_blade_fault ->
    https://github.com/musicalplatypus/tinyml-cli/releases/download/datasets-01_03_00/fan_blade_fault.zip

D-B — Versioning / cache key:
  Preserve the cache-key-includes-version property (a version bump must never silently reuse an
  older cached file). Keep DATASETS_DEFAULT_VERSION = "01_03_00" and keep _cache_dir(version)
  and its <version>/<filename> layout UNCHANGED. What "version" LABELS changes: it is now the
  mirror payload/release version (the release tag is datasets-<version>), no longer TI's engine
  version. Update the DATASETS_DEFAULT_VERSION comment to say so. Because the mirrored bytes are
  byte-identical to what was previously cached under 01_03_00, existing cache entries stay valid
  — a convenience, not a requirement. A future re-mirror bumps the version -> new tag -> new
  cache dir.

D-C — Redirect-handler relaxation (security-relevant; amends 10-02 threat T-10-02-01/05):
  Add an explicit, closed allowlist of permitted cross-host redirect PAIRS keyed on the original
  request host:
    ALLOWED_CROSS_HOST_REDIRECTS = {"github.com": frozenset({"release-assets.githubusercontent.com"})}
  redirect_request permits a redirect iff:
    new_host == self._allowed_host   (unchanged same-host case), OR
    new_host in ALLOWED_CROSS_HOST_REDIRECTS.get(self._allowed_host, frozenset())
  Every other host mismatch still raises the same RuntimeError. NEVER use a suffix/wildcard match
  on githubusercontent.com — pin the exact host so the rule stays narrow and testable. sha256
  verification remains mandatory and is the real integrity guarantee; the host-lock is defence
  in depth, relaxed for exactly one verified hop.

D-D — Is `ti_name` still meaningful?
  KEEP `ti_name`. It is no longer used for URL composition (D-A uses `filename`), but it is still
  load-bearing in TWO ways and must not be removed:
    1. Fetchable-sentinel: _validate_registry (REQ-DATA-02) and dataset_url both treat
       "has ti_name" as "has an upstream and must carry sha256/bytes" / "is fetchable".
       generic_audio_classification (no ti_name) stays bundled-only.
    2. Provenance: it records the original TI asset name the mirrored bytes came from.
  Update the module docstring / dataset_url comment to state plainly that ti_name is now the
  fetchable-sentinel + provenance record and is NOT the URL source. No dead/ambiguous field is
  left: filename is the URL/cache/asset name; ti_name is sentinel+provenance; ti_version is the
  (unused-by-any-entry) per-entry version override, still honoured by default.
</design_decisions>
