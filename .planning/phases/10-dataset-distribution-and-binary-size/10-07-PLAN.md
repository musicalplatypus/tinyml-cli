## Background

There is no release-process document at all. D-3 makes the version axis TI's engine version,
which means every release has to answer: does `DATASETS_DEFAULT_VERSION` move, do any digests
change, and do the pinned URLs still resolve.

Sphinx already autodocs `mmcli.datasets` (`docs/mmcli.rst:39-42`), so new public functions
appear automatically provided their docstrings are written. Phase 3 set the bar at "builds
cleanly with no warnings", which `-W` enforces.

  <action>
Create `docs/RELEASING.md` covering the dataset obligations of a release:

1. **Cutting a release** — decide whether `DATASETS_DEFAULT_VERSION` should move to a newer TI
   engine version. Datasets that should stay on the old version get a per-entry `ti_version`
   override.
2. **Digests are the contract.** If TI republishes a file its sha256 changes and every client
   fails verification loudly. That is intended — mmcli must never install unexpected data —
   but it means bumping the version requires re-recording digests, and the error a user sees
   should be traceable back to this step.
3. **Run the gate after any version or digest change**: `python3
   scripts/verify_dataset_digests.py`. Name the script explicitly. The check that exists only
   as a description is the check that does not get run.
4. **Adding a new dataset** — add the registry entry with `filename`, `ti_name`, `sha256`
   (`shasum -a 256`) and `bytes`, then confirm `mmcli datasets pull <name>` works from a clean
   cache. The import-time invariant will reject an entry with a `ti_name` and no digest, so a
   half-added entry fails at import rather than at download.
5. **Verification before announcing** — from a machine that has never built the repo:
   `rm -rf ~/.cache/mmcli/datasets` then pull each dataset. TI reorganising paths is the most
   likely breakage and this is what catches it before users do.
6. **Binary size** — `scripts/binary_size_ceiling.txt` is the single ceiling, enforced by
   `tests/test_build_config.py` and the CI release job. Raising it is a decision, not a fix.
7. **If TI ever breaks the URLs** — mirroring the zips to this repo's release assets remains a
   viable fallback; the registry change would be a URL swap, not a redesign. Record this so
   the next person does not have to rediscover that the design leaves the door open.

Explain *why* for each rule. A rule whose reason is unstated gets optimised away by the next
person; the immutability rule in particular looks like pointless bureaucracy until you know
clients cache by digest.
  </action>
